Confirmed failure and boundaries of diagnosis

The homepage and JavaScript assets returned 200, but both /api/social/config and /api/auth/config returned static HTML 404 responses instead of JSON. Application initialization awaited the social configuration endpoint and failed before calling startDemo() or reading the saved demo. Fresh Chromium and the owner's existing Chrome tab displayed “ไม่สามารถดำเนินการได้”. No JavaScript syntax exception or saved-data compatibility failure was reproduced.

The Pages API reported a successful deployment and registered Functions routes. Recent immutable deployments and the isolated Preview also returned API 404s. The underlying Cloudflare reason for these responses is not yet established; quota exhaustion, a billing problem, and a platform outage are not confirmed diagnoses. Historical Pages invocation analytics alone cannot establish current routing health. A blocked Cloudflare analytics beacon was also observed under the existing CSP; it was not the application startup dependency and CSP was not weakened.

Actions actually performed

  1. Confirmed account 23017b53386fb67fc62a52cdd017454c, active custom domain, separate Production/Preview databases, no Production R2 binding, closed real-service flags, and foreign-key integrity using read-only checks.
  2. Rolled back from a555e05 to previously verified d9a11c52722175b93236f8e09e74928430013fba, deployment 3e111666-ad69-49ba-91ca-d2495c561076. Confirmed the changed live SHA and matching assets. API 404s and startup failure persisted; rollback did not restore access.
  3. Added a canary-build-only static fictional-demo recovery contract. On live configuration failure, the browser validates this contract and uses hardcoded disabled real capabilities before entering the existing browser-only demo. Supplied capability flags, identities, or credentials are never trusted. Ordinary non-canary builds contain no recovery marker and fail closed. No backend authorization, CSRF, session, moderation, quota, or media-access code changed.
  4. Validated in separate isolated Preview, then deployed the frontend recovery. Rechecked the live domain, deployment metadata, source asset hashes, fresh and returning browser behavior, and the owner's existing Chrome and in-app tabs. No site-data reset or deletion was used.
